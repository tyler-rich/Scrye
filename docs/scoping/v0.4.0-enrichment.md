> **Scoping document, not an implementation plan.** It fixes the shape of the enrichment
> mechanism before any of it is built, so the three feeds in Track B Phase 1 are built once
> rather than three times. No code, migrations, or endpoints are proposed as final here —
> the recommendations below are what an implementing session should start from, and the
> § Open decisions section names what it must still confirm.

> Scope: **only** the three feeds named in the title. Deliberately out of scope, and not
> designed for here: the fix-first view and noise-controls UI, SARIF export, any Phase 2

> scope (§ 12) precisely so that feature is a small addition later instead of a retrofit

## 1. The one-mechanism argument, and where it stops

The three feeds share a delivery mechanism and **do not** share a key space. Both halves of
that sentence are load-bearing.

**What they share** — and what must be built exactly once:

> a scheduled pull of a public document → parse → atomic replace of a local cache →
> a durable record of when that last succeeded → reads that degrade to "no data" instead
> of failing when the cache is empty or stale.

Every one of those steps is feed-independent. Building it three times is the failure this
document exists to prevent.

**Where the sharing stops.** The instinct is to unify EPSS, KEV and endoflife.date behind
one cache table and one join. That is the wrong abstraction, for a reason deeper than the
key type: **they do not enrich the same object.** [ASSERTED]

- EPSS and KEV enrich a **finding**. They answer "how urgent is *this CVE*," they render as
  columns on a findings row, and they sort and filter a findings list.
- endoflife.date enriches a **target**. It answers "is the thing you scanned still
  supported," it renders as one badge on a scan or target, and it is not a property of any
  individual finding. A 400-finding scan of an EOL base image has **one** EOL fact, not 400.

Wiring endoflife.date through a findings-level join would attach one fact to every row that
happens to share a scan, which is not a join — it is a broadcast. That is the shape that
tells you the abstraction is being forced.

The key-space difference follows from that, and independently confirms it:

| | EPSS | KEV | endoflife.date |
|---|---|---|---|
| Key | `cve_id` | `cve_id` | `(product, releaseCycle)` |
| Does a finding already carry the key? | **Yes**, verbatim in `findings.vuln_id` | **Yes**, same | **No.** Must be derived from scan metadata |
| Match semantics | equality | equality | version-prefix match on cycle, **then** a date comparison against today |
| Attaches to | finding | finding | scan / target |
| Rows | ~280k [UNVERIFIED] | 1,665 [VERIFIED] | ~462 products × cycles [VERIFIED] |
| Replace cadence | daily | on CISA update | rare |

EPSS and KEV are the **same** key space — `findings.vuln_id` holds the CVE ID already, so
the join is an equality against a value that exists. They can and should share one lookup
path, differing only in the table they read.

endoflife.date has **no key in Scrye at all**. There is no product field on any table today,
so the key must be manufactured (§ 6). And the manufacture is not clean: verified at source,
the upstream identifier surface is itself inconsistent between products —
`products/python.md` declares `identifiers:` as `purl:` entries
(`pkg:deb/debian/python3.14`, `pkg:docker/library/python`, …) while `products/debian.md`
declares `cpe:` entries (`cpe:2.3:o:debian:debian_linux`). [VERIFIED — the two files, fetched
2026-08-14] So even *upstream's own* identifiers do not give one uniform lookup.

### The call

**One framework, one shared state table, three typed cache tables — and two read paths, not
three.** [ASSERTED]

Concretely:

- **One** `FeedSource` protocol + sync engine + scheduler hook + import seam. Written once.
- **One** polymorphic table, `feed_sync_state`, keyed by feed name. This is the part that
  *is* genuinely uniform across feeds, and it is the only part that should be polymorphic.
- **Three** typed cache tables — `epss_scores`, `kev_entries`, `eol_cycles` — because their
  columns, their types, and their query patterns differ.
- **Two** read paths: a CVE-keyed batch lookup shared by EPSS and KEV, and a separate
  target-level resolution for EOL — both in § 6.

### Why not one polymorphic cache table

Rejected on four independent grounds, any one of which is sufficient: [ASSERTED]

1. **It breaks EPSS sorting, which is the point of EPSS.** "Sortable and filterable" needs
   `ORDER BY score DESC` against a typed, indexed column. In a `(feed, key, payload_json)`
   table that becomes `ORDER BY CAST(json_extract(payload,'$.score') AS REAL)`. SQLite can
   index that expression, but you would need one partial expression index per feed — three
   indexes on one table, which is three tables wearing a coat.
2. **It pays a JSON parse per row on the hot path.** The measured query plan in § 6
   resolves the EPSS side by `SEARCH e USING PRIMARY KEY`, reading two native REALs. Through
   a JSON payload every row read is a parse.
3. **It makes the file-import seam ambiguous.** § 12's seam is "these bytes, this feed." One
   table for three feeds means one import path that must sniff which feed a file is.
4. **It buys nothing.** The shared code is the *engine*, not the storage. Three
   `CREATE TABLE` statements is not the duplication worth abstracting away; three
   fetch-parse-swap-schedule implementations is, and the framework removes exactly that.

The one thing that *should* be polymorphic — sync bookkeeping — is, via `feed_sync_state`.

## 4. endoflife.date — verified (data and license), partial (API)

Fetched from `raw.githubusercontent.com/endoflife-date/endoflife.date` on **2026-08-14**.

**License: MIT.** The repository's `LICENSE` was fetched verbatim: *"Copyright 2020
endoflife.date contributors"* followed by the standard MIT permission text. The README
confirms *"Licensed under the [MIT License](LICENSE)"*, and the shipped OpenAPI document
declares `license: {name: MIT, url: …/blob/master/LICENSE}`. [VERIFIED]

**A licensing wrinkle that MIT alone does not cover, recorded rather than resolved.** The
same README's Credits section states verbatim: *"Product descriptions are adapted from the
[English Wikipedia](https://en.wikipedia.org/), under [CC BY-SA 3.0]… license."* [VERIFIED]

So the repository is MIT, but a specific *field* within it — product descriptions — is
CC BY-SA 3.0, which carries **both** attribution and **share-alike** obligations that MIT
does not. This matters only if Scrye ingests and displays that field.

**Recommendation: do not ingest product descriptions at all.** [ASSERTED] Scrye's EOL
feature needs dates and cycles, not prose. Declining the field sidesteps a share-alike
obligation entirely for zero feature loss, and is a cleaner answer than carrying a
CC BY-SA notice through the UI and `THIRD_PARTY_LICENSES/`. If a later change does want
descriptions, that is a licensing decision to make deliberately, not a field to add to a
parser. **Ambiguity flagged, not resolved:** whether the v1 API surfaces descriptions under
a different key, and whether the CC BY-SA attribution chain is satisfiable at all for
Wikipedia-derived text in this context, was not determined.

**API status — a real constraint.** The README states verbatim: *"An API is available for
integration with CI platforms. API documentation is available at
<https://endoflife.date/docs/api/v1/>. The API is currently in Beta, and breaking changes
can happen."* [VERIFIED] The OpenAPI document in the repository
(`assets/openapi.yml`) describes the **v0** API and its own `description` says *"The
endoflife.date v0 API is currently deprecated, please use the endoflife.date v1 API."*
[VERIFIED]

**So: v0 is deprecated, v1 is Beta and self-declared unstable.** [ASSERTED] That is an
argument for isolating the EOL parser behind the narrowest possible interface and for the
file-import seam (§ 12) being the *stable* path rather than a nicety.

**v1 response shape is [UNVERIFIED]** — `endoflife.date` was blocked, and the v1 spec is not
in this repository. Verify with `curl -sS https://endoflife.date/api/v1/products/python`
and read `https://endoflife.date/docs/api/v1/` for pagination, cadence, and rate limits,
none of which are known here.

**The v0 schema is verified, and carries two parsing hazards that a v1 parser should assume
until proven otherwise:** [VERIFIED — from `assets/openapi.yml`]

- `cycle` is typed `number | string`. Python's cycles deserialize as **numbers** (`3.9`),
  Ubuntu's as **strings** (`"21.04"`). A parser that assumes string gets `3.9` and one that
  assumes float gets `20.04` wrong. Coerce to string on ingest and never to float — `3.10`
  as a float sorts below `3.9`.
- `eol` is typed `string | boolean`. It is a date **or** `false` (meaning "not EOL"). A
  date-only parser breaks on the supported products, which are the majority.
- The schema's own note: *"There might be some slight variations to this depending on the
  product."*

**Source data shape** (the `products/*.md` YAML frontmatter the API is generated from):
[VERIFIED — `products/python.md`, `products/debian.md`]

```yaml

  - releaseCycle: "3.14"
    releaseDate: 2025-10-07
    eoas: 2027-10-01      # end of active support
    eol: 2030-10-31       # end of life
    latest: "3.14.7"
    latestReleaseDate: 2026-08-05
    pep: PEP-0745         # product-specific customField
```

Debian additionally carries `codename` and `eoes` (end of extended support). **Three
distinct lifecycle dates exist — `eoas`, `eol`, `eoes` — and collapsing them to one boolean
is wrong.** [ASSERTED] Verified illustration: `products/debian.md` gives cycle `12`
(Bookworm) `eol: 2026-07-11`, `eoes: 2028-06-30`. As of this session (2026-08-14) Debian 12
is **past `eol` but inside `eoes`** — and Scrye's own runtime image is
`python:3.14-slim-bookworm`. A naive "past eol ⇒ red" flag would light up on Scrye's own
supported, security-supported base image. Model the three dates; render the distinction.

**Volume.** The sibling `endoflife-date/release-data` repository states verbatim: *"As of
2026-07-30, 398 of the 462 products tracked by endoflife.date have automatically tracked
releases."* So ~462 products, each with a handful to a few dozen cycles — low thousands of

**Update cadence and rate limits: [UNVERIFIED].** The dataset changes when a product's

## 5. Cache schema, sizing, and retention

### Tables

Four new tables. **No change to `findings`, `scans`, or any existing table.** [ASSERTED —
and see § 10, which is the constraint this is honouring.]

```sql
-- Shared, polymorphic: the ONLY table keyed by feed name.
CREATE TABLE feed_sync_state (
    feed             TEXT PRIMARY KEY,          -- 'epss' | 'kev' | 'eol'
    last_attempt_at  DATETIME,
    last_success_at  DATETIME,
    last_error       TEXT,                      -- never contains a URL credential
    record_count     INTEGER NOT NULL DEFAULT 0,
    source_version   TEXT,                      -- e.g. KEV catalogVersion '2026.08.11'
    source_etag      TEXT,                      -- conditional GET (§7)
    source_modified  TEXT,                      -- conditional GET (§7)
    origin           TEXT NOT NULL DEFAULT 'network'  -- 'network' | 'file'  (§12)
);

CREATE TABLE epss_scores (
    cve_id     TEXT PRIMARY KEY,
    score      REAL NOT NULL,
    percentile REAL NOT NULL
) WITHOUT ROWID;

CREATE TABLE kev_entries (
    cve_id              TEXT PRIMARY KEY,
    date_added          TEXT NOT NULL,
    due_date            TEXT NOT NULL,
    known_ransomware    TEXT NOT NULL,   -- store the string; see §2
    vulnerability_name  TEXT NOT NULL
) WITHOUT ROWID;

CREATE TABLE eol_cycles (
    product        TEXT NOT NULL,
    release_cycle  TEXT NOT NULL,        -- ALWAYS text; never float (§4)
    release_date   TEXT,
    eoas           TEXT,
    eol            TEXT,                 -- NULL when upstream says `false`
    eoes           TEXT,
    latest         TEXT,
    PRIMARY KEY (product, release_cycle)
) WITHOUT ROWID;
```

`WITHOUT ROWID` is a **[MEASURED]** decision, not a stylistic one — see below.

Deliberately **not** stored: KEV's `shortDescription`, `requiredAction`, `notes`, `product`,
`vendorProject`, and `cwes`; endoflife.date's product descriptions (§ 4, licensing). Scrye
already has a description on the finding from the scanner, and these fields are the bulk of
the bytes. [ASSERTED]

### What it costs in SQLite [MEASURED]

Measured this session with real KEV data and a synthetic 280k-row EPSS table (§ 13 has the
script; § 13 also has the sandbox-vs-runtime caveat):

| Table | Rows | On-disk | Bytes/row |
|---|---|---|---|
| `epss_scores`, rowid + `UNIQUE(cve_id)` | 280,000 | **17.68 MiB** | 66.2 |
| `epss_scores`, `WITHOUT ROWID` | 280,000 | **10.23 MiB** | 38.3 |
| `kev_entries`, all 11 fields | 1,665 (real) | 1.26 MiB | 792 |
| `kev_entries`, as scoped above | 1,665 (real) | **0.18 MiB** | 113 |
| `eol_cycles` | ~5k (est.) | well under 1 MiB | — |

`WITHOUT ROWID` on `epss_scores` is **42 % smaller and measurably faster to look up**
(2.12 ms vs 2.77 ms for a 1,000-key `IN` lookup). The rowid form stores every CVE ID twice —
once in the table, once in the unique index — for no benefit, since nothing references these
rows by integer id.

**Total steady-state cost: about 11 MiB** on top of the existing database, dominated
entirely by EPSS. That is small in absolute terms — but see § 10, because it is *not* small
relative to what a backup bundle can hold in memory.

### Retention

**Current snapshot only. No history, for any feed.** [ASSERTED]

Each sync fully replaces its table. EPSS at 280k rows/day would reach roughly 100 M rows a
year if snapshots were kept — an unbounded growth curve attached to a display-time
convenience. "How did this CVE's EPSS score move over time" is a genuinely different
feature with a genuinely different data model, and it belongs to whoever asks for it, not to
this one.

The existing `run_retention` (`backend/app/core/retention.py`) prunes **raw scan artifacts**
and is correctly unrelated. Enrichment caches need no retention pass at all — replacement
*is* the retention. Do not wire them into `run_retention`. [ASSERTED]

## 6. How enrichment joins to findings at read time

### EPSS and KEV — batched, never per-row

The read path is `GET /api/scans/{scan_id}/findings`
(`backend/app/api/scans.py:416`), which already pages at `limit ≤ 1000` and returns a
`FindingsPage`. [VERIFIED — read in-session]

**The rule: two extra queries per page, regardless of page size.** [ASSERTED]

After the existing query returns the page's `rows`, collect the distinct CVE-shaped
`vuln_id` values and issue **one** batched lookup per enabled feed:

```python
cve_ids = {r.vuln_id for r in rows if r.vuln_id and _CVE_RE.fullmatch(r.vuln_id)}
epss = {r.cve_id: r for r in db.execute(select(EpssScore).where(EpssScore.cve_id.in_(cve_ids)))}
kev  = {r.cve_id: r for r in db.execute(select(KevEntry).where(KevEntry.cve_id.in_(cve_ids)))}
```

then attach in Python. This is O(1) queries per page, not O(n). Filtering to CVE-shaped ids
first matters: `findings.vuln_id` also holds GHSA ids, Trivy check ids, and secret rule ids
(`backend/app/db/models/scan.py:194` — *"Vulnerability/rule identifier (CVE, GHSA, Trivy
check ID, secret rule ID)"*), and none of those will ever match a CVE-keyed feed.

**Parameter limit is not a concern:** `SQLITE_LIMIT_VARIABLE_NUMBER` measured at **250,000**
on this build, against a page cap of 1,000. [MEASURED] Worth stating only because the
historical SQLite default was 999, which *would* have been a concern — an implementing
session should re-check it on the runtime image rather than inherit this number.

### Sorting and filtering by EPSS/KEV — a real LEFT JOIN, and it is cheap

Batched lookup enriches what a page already contains; it cannot *order* a page, because the
sort must happen before the limit. `ORDER BY epss DESC` therefore needs the enrichment table
inside the paged query:

```sql
SELECT f.*, e.score
  FROM findings f
  LEFT JOIN epss_scores e ON e.cve_id = f.vuln_id
 WHERE f.scan_id = ?
 ORDER BY e.score DESC NULLS LAST, f.id
 LIMIT ? OFFSET ?
```

**Measured: 3.5 ms** for a 100-row page from a 2,500-finding scan, against a 500,000-row
`findings` table and a 280,000-row `epss_scores` table. [MEASURED] Query plan:

```
SEARCH f USING COVERING INDEX ix_findings_scan_severity_vuln (scan_id=?)
SEARCH e USING PRIMARY KEY (cve_id=?) LEFT-JOIN
USE TEMP B-TREE FOR ORDER BY
```

Two things this confirms, both of which matter: **the existing
`ix_findings_scan_severity_vuln` index already covers the driving side** — so this needs
**no new index on `findings`** and therefore no change to the findings table in any form.
And `LEFT JOIN` is the correct operator, not an inner join: a finding with no EPSS row must
still appear, with a null score.

Guard the join behind "enrichment enabled **and** this feed has ≥1 row," so a disabled or
never-synced feed does not add a join to every findings query for nothing.

### endoflife.date — a target-level resolution, not a findings join

Per § 1, EOL does not belong on a findings row. It needs a product identity for the *scan*,
which Scrye does not currently store.

**Recommended source of that identity: Trivy's `Metadata.OS` (`{Family, Name}`,
e.g. `{"debian", "12.15"}`) from the raw scanner JSON, captured at normalize time into a
small side table.** [ASSERTED — and this is a data-model addition, see below]

```sql
CREATE TABLE scan_platform (
    scan_id    INTEGER PRIMARY KEY REFERENCES scans(id) ON DELETE CASCADE,
    os_family  TEXT,       -- 'debian', 'alpine', …
    os_version TEXT,       -- '12.15'
    source     TEXT NOT NULL  -- which scanner field it came from
);
```

Why a side table rather than reading the raw artifact at read time: **retention deletes raw
artifacts while keeping findings** (`backend/app/core/retention.py` — *"The scan rows and
normalized findings are preserved; only the raw artifact files and their metadata rows are
removed"*) [VERIFIED]. An EOL badge derived from the artifact would silently vanish from
every scan older than the retention window. A side table survives it, is populated from data
already in hand at normalize time, and adds nothing to the scan's critical path.

Resolution then runs at read time: map `os_family` → an endoflife.date product (a small,
explicit, in-code mapping — `debian` → `debian`, `alpine` → `alpine-linux`, not a guess),
then find the `eol_cycles` row whose `release_cycle` is a version prefix of `os_version`,
then compare `eoas`/`eol`/`eoes` to today.

> ⚠ **This is the one place this document proposes a new table derived from scan data rather
> than from a feed, and CLAUDE.md § When to ask vs. decide requires a pause on data-model
> choices.** It is strictly additive — nothing on `scans` or `findings` changes — but the
> implementing session must confirm it with the maintainer rather than treat this
> recommendation as approval. Two alternatives were considered and are weaker: reading the
> raw artifact at read time (breaks under retention, as above), and adding a column to
> `scans` (touches an existing table for a feature that may be disabled).

**Unresolved, and flagged rather than papered over:** [ASSERTED] this design covers the
**OS / base-image** case, which is the one the roadmap names first ("flag base images, OS
releases, and runtimes"). It does **not** solve EOL for arbitrary *runtimes and language
packages* inside an image — mapping `pkg_name` → an endoflife.date product for hundreds of
packages is a distinct problem, and upstream's own identifier surface is inconsistent
(§ 1). Ship the OS case; do not let the package case expand this feed's scope.

## 7. Sync scheduling

### Reuse the maintenance tick — do not reuse the scan-schedule machinery

Scrye has two distinct scheduling mechanisms, and enrichment belongs to the second: [VERIFIED
— both read in-session]

1. **`scan_schedules`** (`backend/app/workers/schedules.py`, cron via
   `backend/app/core/cron.py`) — user-defined cron entries that create `Scan` rows and submit
   them to the worker. **Wrong for enrichment.** A feed sync is not a scan: it produces no
   scan row, no findings, no artifacts, consumes no worker slot, and must never appear in
   scan history. Forcing it through would put non-scans in the scans table.
2. **`MaintenanceScheduler`** (`backend/app/workers/maintenance.py`) — a single asyncio task
   on a 60-second tick that already runs the stale-scan watchdog, due schedules, retention,
   and — the exact precedent — the scanner vulnerability-DB refresh.

**Enrichment sync follows `db_update.py`'s shape precisely**
(`backend/app/workers/db_update.py`): a detached task kicked from `tick()`, with its own
interval due-check, at most one in flight at a time, and failures logged rather than raised.
That module's `_maybe_start_db_update` guard — *"a fresh subprocess pair must not stack on
top of an in-flight one"* — applies identically to a multi-MB feed download. [VERIFIED]

### One deliberate divergence from that precedent

`db_update.py` tracks its last run in a **module-level in-process variable**
(`_last_update_monotonic`), and documents the consequence: *"a restart re-checks on the first
tick, which at worst triggers one extra refresh — acceptable for a best-effort job."*
[VERIFIED]

**Do not copy that.** [ASSERTED] Persist last-success in `feed_sync_state` instead. The
trade-off that makes it acceptable for scanner DBs does not transfer:

- A container restart currently costs one extra scanner-DB refresh. For EPSS it would cost a
  full multi-MB re-download **on every restart** — and a crash-looping container would hammer
  a public feed from an unattended deployment. That is a bad citizen, not just waste.
- Operators need to *see* freshness. A staleness indicator (§ 8) cannot read an in-process
  variable that resets on restart.
- Conditional GET (`ETag` / `Last-Modified`, § 5's `source_etag` / `source_modified`) needs
  durable validators. In-process state throws them away at exactly the moment they are most
  useful.

### Cadence

Per-feed, defaulting from each feed's real cadence rather than one shared number: [ASSERTED,
from the cadences verified in §§ 2 and 4]

- **KEV — 6 h.** Updates land on weekday US-Eastern business hours; 6 h bounds staleness to
  part of a business day at 4 requests/day against a 1.5 MB document.
- **EPSS — 24 h.** Regenerated daily. **[UNVERIFIED]** — confirm the publication time of day
  and offset the schedule past it, or a 24 h cycle can settle just *before* each day's
  refresh and run permanently one day stale.
- **endoflife.date — 24 h.** Changes are infrequent and never urgent.

Add jitter to the first check after startup so a fleet of Scrye instances does not
synchronize onto the same second. [ASSERTED]

**Use conditional GET on every feed that supports it.** With `ETag`/`If-None-Match` a daily
EPSS poll costs a 304 rather than a full download whenever the feed has not moved. Store the
validators in `feed_sync_state`; on 304, update `last_attempt_at` only and leave the cache
and `last_success_at` untouched.

### The swap must not block scans

Sync writes to a staging table with no lock on the live table, then swaps in one
transaction:

```sql
BEGIN IMMEDIATE;
DELETE FROM epss_scores;
INSERT INTO epss_scores SELECT * FROM epss_scores_staging;
COMMIT;
```

**Measured on 280k rows: staging 0.35 s (no lock held on the live table), swap 0.17 s (write
lock held).** [MEASURED] Against the configured `busy_timeout` of **5,000 ms**
(`backend/app/db/session.py:22`) [VERIFIED], a 170 ms write-lock window consumes ~3.4 % of
the budget a contending scan writer will wait out. WAL is enabled
(`PRAGMA journal_mode=WAL`, same file) so readers are never blocked at all. Readers see the
old snapshot or the new one, never a partial one.

Note the transient disk cost: the staging table roughly doubles EPSS's footprint during a
sync, and the measurement showed the WAL growing to 11.4 MiB. Both are reclaimed. Budget
~25 MiB of transient headroom, not 11.

## 8. Failure semantics

**The hard rule, and the one this section exists to enforce: a scan's success must never
depend on a network fetch.** This is satisfied structurally rather than by care —
**enrichment is read-time only**. Nothing in `backend/app/scanners/`, nothing in
`backend/app/workers/inprocess.py`, and nothing on the scan submit/execute path calls the
enrichment layer at all. A scan cannot observe a feed's health because it never asks.
[ASSERTED]

That is a design invariant worth a test: assert that the scan execution path performs no
enrichment lookup, so a later refactor cannot quietly introduce the dependency.

Every other failure degrades to "no data," never to an error: [ASSERTED]

| Condition | Scan | Findings API | UI |
|---|---|---|---|
| Feed host unreachable / DNS fails | unaffected | 200, serves the **last good cache** | staleness badge with `last_success_at` |
| Feed returns 5xx or times out | unaffected | 200, last good cache retained | error text from `feed_sync_state.last_error` in Settings |
| Feed returns malformed or truncated body | unaffected | 200, **previous cache retained** — never half-replaced | sync error surfaced |
| Feed never synced | unaffected | 200, `enrichment.epss = null` | "not yet synced" |
| Sync in progress / mid-swap | unaffected | 200, old or new snapshot, never partial | — |
| Enrichment disabled | unaffected | 200, `enrichment: null` | column hidden entirely |
| Egress guard refuses the URL | unaffected | 200, last good cache | guard's message in `last_error` (§ 9) |

Three specifics that make the table true rather than aspirational: [ASSERTED]

- **Parse fully before touching the live table.** Staging exists for correctness, not just
  for lock duration: a body that parses for 240k rows and then fails must leave the previous
  280k-row snapshot completely intact.
- **A sanity floor on record count.** A successful HTTP 200 that yields near-zero rows is far
  more likely to be an error page than a real empty feed. Refuse to swap in a snapshot below
  a per-feed floor, log it, and keep the old data.
- **Bound the download.** Stream with a hard byte cap (§ 11) and abort past it, rather than
  reading an unbounded body into memory. `backend/app/api/uploads.py`'s
  `read_upload_capped` is the existing precedent for this shape. [VERIFIED]

Staleness must be **visible, not silent**: surface `last_success_at` per feed in the
Scanners/Enrichment settings pane and as a subtle indicator wherever enrichment renders. A
silently-frozen EPSS score is worse than an absent one, because it looks current. [ASSERTED]

## 9. Interaction with the egress guard

The task asked for this explicitly, so it is stated precisely. All of the following is
[VERIFIED] by reading `backend/app/core/egress.py` and its four call sites in-session.

### Do these fetches pass the guard as-is? Yes.

`validate_egress_host()` resolves the target and refuses **loopback, link-local (which is
where the cloud-metadata address lives), multicast, unspecified, and reserved addresses
always**, and **private (RFC-1918 / ULA / CGNAT) addresses unless `allow_internal`**. A host
resolving to an ordinary public address hits none of those branches and `_blocked_reason`
returns `None`.

`api.first.org`, `www.cisa.gov`, `raw.githubusercontent.com` and `endoflife.date` are public
internet hosts resolving to public addresses. **They pass the existing guard unchanged. No
allowance, no new setting, and no code change to `egress.py` is required.**

### What `SCRYE_ALLOW_INTERNAL_EGRESS` does and does not have to do with it

**It has nothing to do with the default case, and it must not be presented as an enrichment
prerequisite.** [ASSERTED] Its only effect is to widen the guard to permit
RFC-1918/ULA/CGNAT destinations (`config.py:178` — *"Allow server-side fetchers … to reach
RFC-1918/private/internal addresses"*). A public feed host never triggers that branch, so
the flag changes nothing about a default enrichment deployment. Documenting it as something
an operator must enable for enrichment would be actively wrong and would push deployments
into widening their SSRF posture for no reason.

**Where it does become relevant — and it is exactly the right control when it does:** an
air-gapped or restricted deployment pointing a feed URL override (§ 11) at an **internal
mirror** on the LAN. That host resolves to a private address, the guard refuses it, and the
error message the guard already emits says what to do —
*"set SCRYE_ALLOW_INTERNAL_EGRESS=1 to allow internal targets"* (`egress.py:103`). No new
knob. Document that as the internal-mirror path and leave the flag's default `false` alone.

### What the implementation must actually do

1. **Call the guard.** Every enrichment fetch goes through
   `await validate_egress_url_async(url, allow_internal=get_settings().allow_internal_egress)`
   — the identical shape used by `notifications.py:56` and `registry_check.py:107`. This is
   not optional: the feed URLs are **operator-configurable**, which makes them exactly the
   admin-supplied-URL surface the guard was built for (M5 / SEC-6, `docs/ARCHIVE.md` §14
   2026-07-13).
2. **Do not pass `allow_internal=True`.** That literal is the Docker socket proxy's special
   case (`docker_proxy.py:89`), justified there because the sidecar is internal by design.
   An enrichment feed has no such justification.
3. **Do not follow redirects blindly — this is the real gap.** The guard validates the host
   *you asked for*. An HTTP redirect moves the connection to a host the guard never saw, so
   a feed that 302s can land on loopback or `169.254.169.254` with the guard fully satisfied.
   `registry_check.py:113` already sets `follow_redirects=False` for this reason [VERIFIED].
   Enrichment must do the same: disable automatic redirects, and on a 3xx, re-validate the
   `Location` host through the guard before following, with a small hop cap. **This matters
   concretely for EPSS**, whose bulk URL may well redirect (§ 3 lists confirming that as a
   required check).
4. **Do not follow the OIDC precedent.** `backend/app/auth/oidc.py` opens three
   `httpx.AsyncClient` connections with **no egress validation at all** (lines 95, 127, 185)
   [VERIFIED]. Whether that is deliberate — an OIDC issuer is plausibly internal — or a gap
   was not determined in this session and is **out of scope for this document**; it is noted
   only so an implementing session does not cite it as the house pattern. The guarded call
   sites are the pattern.
5. **The guard is best-effort, and the module says so.** Its own docstring: *"Resolution
   happens here and httpx re-resolves when it connects, so this is a best-effort,
   defense-in-depth control (not DNS-rebinding-proof)"* [VERIFIED]. Enrichment inherits that
   property and should not be documented as stronger than it is.

## 10. What this does not change

Stated explicitly because these were hard constraints on this scoping session, and because
"additive only" is the property that makes the whole design safe to land.

- **The `findings` table's own schema is untouched.** No new column, no new index, no type
  change. § 6's measurement confirms none is needed — the existing
  `ix_findings_scan_severity_vuln` already drives the sort join. Enrichment attaches at read
  time, in the response model, via an additive optional `enrichment` object on `FindingOut`.
- **Nothing is denormalized onto findings.** Beyond the schema constraint there is a
  correctness reason: a finding is a **scan-time fact**, while EPSS changes daily and KEV
  changes weekly. Writing today's EPSS score onto a finding row would either freeze it
  (making an old scan's score silently wrong) or require rewriting historical scan data on
  every sync. Read-time join is the only shape where a two-year-old scan and today's score
  are both correct.
- **No locked decision is touched.** SQLite stays; the in-process worker stays; no new
  binary, sidecar, or service; no new secret material (all three feeds are unauthenticated
  public documents, so nothing enters the field-encrypted secret store).
- **No scan's success depends on a network fetch** (§ 8).
- **No new outbound-egress capability.** § 9 — the existing guard covers this unchanged.

### One thing it *does* change, which must not be missed

**Backup.** `backend/app/backup/bundle.py:141` builds a bundle from
`Base.metadata.sorted_tables` **minus an explicit exclusion list** — so a new table is
included in every backup **by default**, silently. [VERIFIED]

That is the wrong outcome here, on two grounds:

1. **Memory.** The bundle is *"assembled and encrypted in memory in a single pass"*, and the
   module already warns past **250,000 findings rows** (`_FINDINGS_WARN_THRESHOLD`)
   [VERIFIED]; `docs/ROADMAP.md` carries "Framed streaming backup encryption" as an open item
   for exactly this. Adding 280k EPSS rows would **more than double the row count of a
   moderate instance's bundle** with data that is not the operator's.
2. **It is not user data.** Every enrichment row is a re-fetchable copy of a public feed.
   Restoring a stale EPSS snapshot from a six-month-old bundle is strictly worse than
   restoring nothing and re-syncing.

**Therefore: add all four new tables — `epss_scores`, `kev_entries`, `eol_cycles`, **and**
`feed_sync_state` — to `_EXCLUDED_TABLES`.** [ASSERTED] `feed_sync_state` is included in the
exclusion deliberately: restoring it onto a host with an empty cache would assert a
`last_success_at` that never happened on that host, which is precisely the false-freshness
failure § 8 is built to avoid.

This is a small change to one frozenset, and it is the single easiest thing in this document
to forget. `scan_platform` (§ 6) is the opposite case — it *is* derived from the operator's
scans and **should** travel in a backup, so it stays out of the exclusion list.


### API response shape

Additive and envelope-compatible with `CONTRIBUTING.md` § API conventions — `FindingsPage`
stays a `Page[FindingOut]`, and `FindingOut` gains one optional object: [ASSERTED]

```jsonc
{
  "id": 42, "severity": "critical", "vuln_id": "CVE-2021-44228",
  "enrichment": {
    "epss": { "score": 0.97, "percentile": 0.999 },
    "kev":  { "date_added": "2021-12-10", "due_date": "2021-12-24",
              "known_ransomware": "Known" }

```

`enrichment` is `null` when enrichment is disabled, and each inner key is `null` when that
feed has no row for the finding. **The distinction is deliberate** — `"enrichment": null`
means "the operator turned this off," `"enrichment": {"epss": null}` means "on, but this CVE
is not scored." A client that cannot tell those apart will render the wrong empty state.

`GET /api/enrichment/status` returns the per-feed `feed_sync_state` rows for the Settings
pane. Per `CONTRIBUTING.md` § API conventions this is a **fixed enumeration of three feeds,
not a growing resource collection**, so it stays a bare array rather than taking the
`{total, items}` envelope — the same call as `/api/notifications/events`. [ASSERTED]

## 12. The file-import seam

The air-gapped import *feature* is out of scope. The **seam** is in scope, and it is nearly
free if the engine is shaped correctly from the start — and a painful retrofit across three
parsers if it is not.

**The seam is one rule: the parse-and-swap path must be a pure function of bytes, with no
network in it.** [ASSERTED]

```python
class FeedSource(Protocol):
    name: str                                   # 'epss' | 'kev' | 'eol'

    async def fetch(self) -> bytes: ...         # network; egress guard lives HERE and only here
    def parse(self, raw: bytes) -> list[Row]: ...   # pure; no I/O
    def swap(self, db: Session, rows: list[Row], *,
             origin: FeedOrigin,                 # 'network' | 'file'
             source_version: str | None) -> None: ...  # staging + atomic swap
```

Given that split, the air-gapped import later is *only* a new caller:

```python
raw  = import_path.read_bytes()          # instead of: raw = await source.fetch()
rows = source.parse(raw)
source.swap(db, rows, origin="file", source_version=None)
```

Two properties make it genuinely usable rather than nominally present: [ASSERTED]

1. **The import accepts the byte-for-byte format the network endpoint serves** — gzipped CSV
   for EPSS, JSON for KEV, JSON for endoflife.date. An operator can `curl` the feed on a
   connected machine, copy the file across, and drop it in. No conversion step, no
   Scrye-specific format, and the same parser is exercised by both paths, so the offline path
   cannot rot untested.
2. **`feed_sync_state.origin` records which path fed the cache**, so the UI can say
   "imported from file, 2026-08-14" rather than implying a successful network sync.

Provisioning it now costs: the `origin` column (already in § 5's schema), the `Protocol`
split above, and keeping `parse()` free of I/O. That is the entire investment. Retrofitting
it later means unpicking fetch-from-parse in three separate feed implementations, which is
precisely the "build it three times" outcome this document exists to prevent.

`SCRYE_ENRICHMENT_IMPORT_DIR` defaults to `/data/feeds` — on the existing persistent `/data`
volume (`docker/docker-compose.yml`), so no new mount, no Compose change, and no change to
the read-only-root-filesystem posture. [VERIFIED]

Every **[MEASURED]** number came from a script run in this session. Reproduce or re-run with:

be re-checked on the runtime image rather than inherited from the 250,000 measured here.
